# MOBILE — the store shells around the live site

The stores get a thin native shell, not a second app. Each shell is a WebView
that opens `https://podium.bftmiddleeast.com/results` full-screen under the
PODIUM icon, so **the website is the app**: a web deploy reaches every install
immediately, with no store review and nothing to upload. A store release is
only needed when the shell itself changes — a native plugin, an icon, a
permission.

This is deliberate: the web app is server-rendered Next.js with API routes and
a database, so it cannot be bundled into an offline binary without a rewrite.
Loading the live site keeps one app and one deploy pipeline.

## Day to day

**A normal web change needs nothing.** Deploy the site as usual; installs
picked it up the moment the deploy landed.

**Changing the shell** (start URL, allowed hosts, bundle id): edit
[capacitor.config.ts](../capacitor.config.ts), then `npm run mobile:sync`, and
make a store release per platform below.

**Adding a native capability** (push, camera, …): `npm i @capacitor/<plugin>`,
`npm run mobile:sync`, then a store release. Push notifications would also
need FCM setup on Android (drop `google-services.json` into `android/app/` —
the Gradle file already applies the plugin when it is present) and an APNs key
on iOS.

## Android release

One-time, on the repo:

1. Create an upload key: `keytool -genkey -v -keystore podium-upload.jks -keyalg RSA -keysize 2048 -validity 10000 -alias podium`. Keep the keystore and passwords safe — losing them means losing the ability to update the listing.
2. Add four repository secrets: `MOBILE_KEYSTORE_BASE64` (the `.jks`, base64-encoded), `MOBILE_KEYSTORE_PASSWORD`, `MOBILE_KEY_ALIAS`, `MOBILE_KEY_PASSWORD`. CI materializes them into `android/keystore.properties`, which `app/build.gradle` picks up; without them the AAB still builds, but unsigned.

Every release:

1. Bump `versionCode` and `versionName` in `android/app/build.gradle` — Play rejects a reused `versionCode`.
2. Tag `mobile-v<version>` (or run the workflow by hand) and download the `podium-release-aab` artifact.
3. Upload the AAB in Play Console as a new release. Copy the SHA-256 of the upload key from Play Console → Setup → App signing into [assetlinks.json](../public/.well-known/assetlinks.json) if you ever want verified deep links; the shell itself does not need it.

## iOS release

The automated release runs on GitHub's `macos-15` runner with Xcode 26 and Swift
Package Manager (no CocoaPods). Follow [MOBILE-APPLE.md](MOBILE-APPLE.md) for
the CSR, certificate/profile creation, API key, repository secrets and exact
workflow commands. The existing record is version 1.0; CI advances the build
number without changing the marketing version.

For a local Mac release:

1. `npm ci && npx cap sync ios`, then `npm run mobile:ios` (or open `ios/App/App.xcodeproj`).
2. Signing & Capabilities: pick the team, let Xcode manage the certificate.
3. Use marketing version **1.0** for this release and a fresh build number in the target's General tab.
4. Product → Archive → Distribute App → App Store Connect. TestFlight first: install on a real iPhone, sign in, enter a live round.
5. Submit for review with notes framing it as the official PODIUM live-results companion (live board, score entry, results), not a bookmark.

The honest risk: Apple's 4.2 "minimum functionality" rule exists for apps that
are just a website in a box. If a build is rejected, the fallback is already
live — Safari → Share → Add to Home Screen gives iPhone users the same
icon-and-full-screen experience with no review at all, and web push works from
iOS 16.4. The store listing is presence, not a dependency.

## In-app announcements

Phase 1 is an in-app inbox. No OS push, email, third-party scripts or automatic
event triggers are added. A normal web deployment brings it to the PWA,
Android shell and iOS shell together.

Staff open **Announcements** from the studio competition sidebar or
`/studio/announcements`; BFT MENA uses `/announcements` in the platform console.
Default studio staff can compose only for their own studio. Admins choose all
signed-in users, one account role, or one active studio. Custom studio access
roles need `announcements.view` and `announcements.manage` to compose and send;
view alone permits sent-history access. Competitor accounts cannot send.

The bell appears in console/account headers and, for signed-in viewers, the
public results header used by both shells. Guests can continue viewing results
without an account. Inbox pages and unread counts are filtered on the server
by the account's current role and assigned studio. The inbox polls every 30
seconds while closed and refreshes on opening, navigation and returning to the
app. It supports older pages, individual read receipts and marking shown
messages read. Read state lives in MySQL per account across all devices. Admin
role previews can inspect an inbox but cannot send or mark messages read.
Interface strings use the existing English/Arabic dictionary; authored message
text stays as written and is rendered as plain text.

For the gated web deployment:

1. Back up the production database using the existing operations process.
2. From a release checkout containing this migration, run `npx prisma migrate
   deploy` with the production datasource before serving the new code. The new
   `20260917030000_notifications` migration adds `Notification` and
   `NotificationRead` with audience indexes and foreign keys; it does not alter
   existing scores or registrations.
3. Deploy the verified production build as usual. Do not serve the new code
   against a database lacking these tables. Client generation is included in
   `npm run build`.
4. Sign in as BFT MENA, send a test announcement to one studio, and verify that
   an account in that studio sees the bell/count while another studio does not.
5. Mark it read and reopen on another device. Repeat with role/all audiences,
   English and Arabic, then install and check the Android and iOS test builds.
   A read-only admin preview must leave the unread count unchanged.

The production migration and website deployment remain manual/gated. Local
verification does not establish that this feature is already live.
